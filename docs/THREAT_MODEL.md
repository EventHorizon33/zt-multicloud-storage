# Threat Model

## Assets

| Asset | Where it lives | Protection goal |
|---|---|---|
| File plaintext | Only transiently in backend memory / the download spool (an unlinked temporary file under `<data_dir>/tmp`; for a large file it holds the whole plaintext on disk until the download ends) | Confidentiality, integrity |
| Encrypted chunks | Three storage providers | Integrity, availability |
| Data keys (DEK) | Wrapped in metadata DB; plaintext only in backend memory | Confidentiality |
| Master keys (KEK, signing, HMAC) | KMS keystore, encrypted under a root key supplied out-of-band | Confidentiality |
| Manifests and file metadata | Metadata DB (filename/MIME encrypted, manifest MAC'd) | Integrity; confidentiality of names |
| Credentials and sessions | Metadata DB (Argon2id hashes, token HMACs) | Confidentiality |
| Audit log | Separate audit DB, checkpoints anchored to providers | Integrity, privacy |

## Trust assumptions

Trusted: the backend process, its host, the KMS root key, TLS termination in
front of the backend, and -- only when `ZT_TRUST_FORWARDED_FOR=true` -- exactly
`ZT_TRUSTED_PROXY_HOPS` appending proxies (optionally pinned with
`ZT_TRUSTED_PROXY_CIDRS`; ADR-0011). Every `X-Forwarded-For` entry left of
those hops, and any peer address (loopback included), is untrusted. Untrusted: storage providers, their credentials once
leaked, the network, clients, and the *contents* of both databases as far as
integrity is concerned.

## Threats and controls

| Threat | Attack | Controls | Residual risk |
|---|---|---|---|
| **Compromised user credentials** (the UNC5537 path) | Stolen password replayed | MFA required at sign-in by default (`require_mfa_for_login=true`, ADR-0010): a password-only session can only read `/me`, log out, enrol MFA (gated) and read the policy -- session list/revoke and password change answer `403 mfa-required` (review M5; before the fix this sentence was not true). Password change needs a factor verified within the step-up window, is refused for accounts without a factor, and never revokes a session that verified the factor more recently than the caller (review H1). Step-up MFA for sensitive actions (download of confidential+ files, delete, share, admin). Short tokens, session idle/absolute expiry, refresh reuse detection, lockout (attempts reserved atomically before verification, so parallel guesses cannot exceed it, review L3), bulk-download detection. Network allow list enforced on login, refresh (checked before reuse detection, review L2), `/me`, session list/revoke (review L1), password change and MFA endpoints as well as on every PDP-gated route (F2); the client IP behind proxies per ADR-0011 (review H2) | If an operator turns `require_mfa_for_login` off, a user who never enrols MFA can log in and read their own `public`/`internal` files with a password alone (but still cannot manage sessions or change the password). A thief who holds the second factor too is indistinguishable from the owner |
| **MFA enrolment hijack** (stolen password used to register the attacker's authenticator, F1) | Log in with the password, enrol and activate a TOTP factor the attacker holds | ADR-0010: activation never makes the session MFA-verified and never revokes the owner's sessions; self-enrolment only within 24 h of registration (TOFU) for accounts that never had a factor, or for the bootstrap admin while no other admin holds a factor; otherwise a single-use admin-issued enrolment code; replacing a factor needs a code from the current one; admin MFA reset for recovery; every enrol/activate audited at WARNING with the source network | **TOFU window:** a password stolen within 24 h of registration, before the owner enrols, lets the thief enrol their own factor and then step up with it (detected and recoverable, not prevented; `test_s11_stated_limit_tofu_window`). **Bootstrap admin:** until it enrols, its password alone can establish the admin factor. **Admin enrolment codes are a privileged path:** an admin with fresh MFA can let any non-admin account be enrolled by whoever holds the code; issuance and use are audited, and the code's delivery channel is outside the system |
| **Account enumeration** | Probe registration with a leaked username list | Registration answers a uniform `202 {"status":"accepted"}` with the same Argon2 work whether or not the name exists (F3); login and share already hide existence; self-registration can be switched off (`allow_self_registration`) | DB query timing differences are not padded. Users cannot learn from the API whether their own registration created an account (they find out by signing in) |
| **Stolen access token** | Replay of a bearer token | 5-minute lifetime; session checked on every request so logout/revocation is immediate; optional IP binding | Usable for up to 5 minutes from an allowed network if not revoked. Tokens are bearer tokens: no proof-of-possession (DPoP/mTLS) is implemented |
| **Malicious authenticated user** | Reads others' files; guesses file IDs; mass download | Ownership + explicit share check on every operation; unknown and unauthorised IDs both return 404; rate limits; download anomaly detection and temporary block | Can exfiltrate whatever they are legitimately entitled to, up to the detection threshold. Encryption cannot prevent an authorised user from keeping plaintext they downloaded |
| **Bulk export from a stolen account under the large-file deployment** | A valid session downloads many large files | The detector blocks a user after `detect_max_downloads_in_window` downloads (20) or `detect_max_download_bytes_in_window` bytes in 5 minutes. The framework default (512 MiB) also blocks any single file above it. The container deployment raises it to 20 GiB so files up to 10 GiB can be served (ADR-0012): the volume limit is then about 40 times weaker, the count limit is unchanged. Accepted for that deployment; revert by removing the setting. |
| **Compromised storage-provider credential** | Reads, modifies, deletes or replaces objects at one provider | Provider holds ciphertext of a subset of chunks under opaque random names, no keys, no filenames, no owner IDs. Modification detected by SHA-256 + AES-GCM tag; substitution/reordering detected by AAD binding; deletion tolerated via second replica (R=2) | Provider learns object count, sizes (≈ chunk size) and access timing. Deleting objects at **two** providers that hold both replicas of a chunk makes that file unrecoverable (detected, not prevented). With R=2 of 3, each provider holds about two-thirds of all ciphertext chunks |
| **All three provider credentials compromised** | Collects every ciphertext chunk | Still no keys: DEKs are wrapped by a KEK held only in the KMS | Availability can be destroyed; confidentiality holds as long as the KMS root key is safe |
| **Metadata DB compromise (read)** | Dumps the database | Passwords Argon2id; refresh tokens stored as HMAC; TOTP seeds KMS-encrypted; DEKs wrapped; filenames/MIME encrypted | Reveals usernames, roles, file sizes, chunk locations, classification labels, sharing relationships |
| **Metadata manipulation (write)** | Edits manifest, chunk order, locations, owner, swaps wrapped keys between rows | Manifest HMAC under a DEK-derived key; DEK unwrap context binds file ID and owner ID, so a key moved to another row or a changed owner fails to unwrap | An attacker with DB write access can change `users.role`, grant themselves shares, or reset a password hash, then act through the API as that identity. This is detected only after the fact through the audit trail (the audit DB is separate). Row-level MACs on users/shares are not implemented |
| **Chunk substitution / reordering / truncation / rollback** | Swap chunk A for chunk B, drop the last chunk, replay an old object | Per-chunk AAD = (format version, file ID, index, final flag); manifest fixes count and hashes; whole-file SHA-256 | Rollback of a *whole file* to an older version is not applicable: files are immutable (no versions) |
| **Audit-log tampering** | Modify, delete, reorder, or truncate records | Hash chain; Ed25519-signed checkpoints; checkpoints anchored to storage providers in a per-log namespace `anchors/audit/<log_id>/` so deployments sharing a bucket cannot overwrite each other's anchors (F4, ADR-0006 amendment); separate audit DB | An attacker controlling the audit DB **and** the audit signing key **and** every anchor copy can rewrite history. Records written after the last anchored checkpoint can be truncated without detection until the next checkpoint (window = `audit_checkpoint_every` events) |
| **Malicious or compromised administrator** | Reads user files; hides tracks | Admin role has no `file:read` on others' files and no API path to keys; role changes, policy changes, key rotation and retention runs are audited; admins cannot edit audit records through the API; the audit-pseudonym key cannot be rotated through the API (offline, two-person operation; lookups match every retained key version, so an out-of-band rotation does not orphan history: ADR-0007 amendment, review M3); auditor role is separate | An admin can promote an account, disable users, loosen policy thresholds (audited). An operator with **host access** to the backend can read the root key and process memory and is out of scope (see below) |
| **Insider with host/DB access** | Direct database or filesystem access | Separation of stores (metadata DB, audit DB, KMS keystore, providers); root key supplied by environment/secret file, not stored with data | Someone holding the root key, the keystore and the metadata DB can decrypt everything. Mitigated in production by an external KMS/HSM (the AWS KMS adapter), not by this codebase alone |
| **Denial of service** | Login floods, upload floods, large uploads, provider outage, invalid-token floods against the audit log, provider-egress amplification | Per-client-network (IPv4 address, IPv6 /64: review L4) and per-user rate limits (rejections audited: first 429 per key per window as `security.rate-limited`, the rest as one summary, F6); requests with invalid bearer tokens limited per client network and refused before any verification work once over the limit, their `auth.token` events aggregated the same way (review M2); the security centre returns critical events in a separate list so they cannot be pushed out; file verify/repair and audit export rate limited per user (review L6, L7; the own-scope export filters in SQL); upload size cap; malformed multipart and out-of-range integers are 4xx, not 500 (review I1, I2); bounded retries with backoff, provider health tracking and failover, lockout. Logins from outside a user's allow list do not count towards lockout | Rate limiting and its audit aggregation are in-process (per instance), not distributed. While a network is over the invalid-token limit, legitimate users behind the same address (NAT) or IPv6 /64 are refused too, until the bucket refills. Lockout can be abused from an allowed network to lock a victim out (mitigated by lockout being time-boxed). No protection against volumetric network attacks |
| **Token forgery / algorithm confusion** | `alg:none`, HS256-with-public-key | Algorithm pinned to EdDSA; issuer, audience, expiry, type claims validated; signing key held in KMS | — |
| **Path traversal / unsafe filenames** | `../../etc/passwd` as filename | Filenames are never used as paths or object keys; stored only encrypted; sanitised for `Content-Disposition` | — |
| **Unattributable storage alerts** | Investigator cannot tie `storage.replica.corrupt` to a request or user | Ambient per-request audit context propagated into the storage thread pools: storage events carry request id, actor pseudonym and source network (F5) | Events from background threads (health monitor, maintenance) carry no request context by design |
| **Re-identification by auditors** | Map audit pseudonyms back to accounts without the audited path | Auditors hold no `user:list`; the user directory carries no pseudonyms; the only mapping is the admin-only, fresh-MFA, always-audited pseudonym lookup (ADR-0007 amendment, review M1) | Usernames and roles in other views (e.g. file shares) can still let an insider correlate behaviour with a person by context |
| **Forged request correlation** | Reuse a victim's request id so their audit records mix with the attacker's | The audit `request_id` is always server-generated; a client `X-Request-ID` is kept apart as `details.client_request_id` (review L8) | — |
| **Metrics exposure** | Read operational metrics from the Internet through a same-host proxy | `/metrics` needs `ZT_METRICS_TOKEN` or an admin access token; the peer address is never trusted (review L5) | The scrape token is a static bearer secret; rotate it with the deployment's secret manager |
| **Insecure default configuration** | Deploy without setting `ZT_ENV` | Default `env=production`: no auto-generated root key (startup fails without one), no `/docs`/`/openapi.json`, HSTS on (review M4) | — |
| **Secrets in logs** | Tokens, passwords or keys written to audit or app logs | Audit privacy filter with allow-listed fields and a deny-pattern scan; structured app logging with redaction; tests assert secrets never appear | A developer adding a new allow-listed field could introduce a leak; the test suite scans audit output for known secrets to catch this |

## What this system does NOT protect against

1. **An authorised user misusing plaintext** after a legitimate download.
2. **Compromise of the backend host or process memory.** The backend sees plaintext and data keys during upload and download. This is application-side encryption, not end-to-end client-side encryption: a malicious backend operator can read data in transit through it.
3. **Compromise of the KMS root key together with the metadata DB.**
4. **Loss of more replicas than the replication factor tolerates.** There is no erasure coding; nothing is reconstructed from parity.
5. **Traffic analysis.** Providers and network observers see object sizes, counts and timing.
6. **Endpoint compromise** (the infostealer itself). The system limits what a stolen password or token is worth; it cannot stop the theft.
7. **Multi-instance deployments** without extra work: rate limiting, lockout counters and audit-append serialisation assume a single backend instance (or Postgres advisory locking for the audit chain).
8. **Transport security.** TLS must be terminated in front of the backend; the application does not manage certificates.
9. **Real-cloud IAM misconfiguration.** The bucket policies and IAM roles for real deployments are documented as guidance, not provisioned or verified by this project.
